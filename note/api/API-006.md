`diana_bisection`, `diana_newton`, `diana_euler` and `diana_rk4` loop over the verified
reverse-communication kernels with a C callback. They are ordinary tested code: no WP
expectation row, no Clight AST, no VST proof. The callback is a trust boundary.

- Callback types: `diana_bisection_fn` is `double (*)(double x, void *ctx)`
  (`diana/bisection.h`); `diana_newton_fn` is `double (*)(double x, double *dfx, void *ctx)`
  (`diana/newton.h`); `diana_ode_fn` is
  `void (*)(double t, const double *y, double *dy, size_t d, void *ctx)` (`diana/ode.h`). `ctx`
  is passed through untouched, so parameters need no globals.
- Each first sets its optional count (`*iter` or `*done`) to 0, then returns `DIANA_ERR_ARG`
  before any callback call for a NULL callback, a NULL `root` (root finders), or a NULL `y`,
  NULL `work` or `d == 0` (ODE wrappers).
- A callback has no error channel: it can signal failure only by a NaN or infinite value, which
  the next kernel call rejects with `DIANA_ERR_ARG`. A `diana_ode_fn` must write all `d`
  components of `dy`, since the ODE wrappers do not initialise `work`.
- The wrappers call only the checked kernels, never the `_unchecked` variants.
- The Python functions `diana.bisection`, `diana.newton`, `diana.euler` and `diana.rk4` do not
  call these wrappers: each runs its own loop in Python over the extension.
