`diana_euler_step_unchecked`, `diana_rk4_stage_unchecked`, `diana_rk4_step_unchecked` and
`diana_axpy_unchecked` take the arguments and aliasing rules of their checked counterparts and
differ only in skipping the finiteness check.

- They return `DIANA_ERR_ARG`, writing nothing, exactly for a NULL pointer, `d == 0` (not axpy,
  whose `n == 0` is valid) and (stage) a `stage` outside 2 to 4. Otherwise they make one pass that computes each component in the
  checked operation order, writes it, NaN and ±∞ included, and return `DIANA_OK`
  (EULER-UNCHECKED-C1, RK4-UNCHECKED-C1, C2, AXPY-UNCHECKED-C1). `DIANA_OK` says nothing about
  finiteness.
- They call no function, not even `diana_fp_finite`; so `diana_axpy_unchecked` does not test
  `a` as `diana_axpy` does (API-039), and accepts a NaN `a` with `n == 0`.
- Where the checked kernel returns `DIANA_OK`, both write the same bits: VST proves both write
  the same C-order model (EULER-C2 and EULER-UNCHECKED-C2; RK4-C3/C4 and RK4-UNCHECKED-C3/C4;
  AXPY-C2 and AXPY-UNCHECKED-C2, the latter through `c_euler` with the arrays swapped).
- A written component is finite exactly when its inputs are finite and no operation overflowed
  (EULER-UNCHECKED-B1, RK4-UNCHECKED-B1, B2, AXPY-UNCHECKED-B1). So testing `y_out` (or `y`)
  for finiteness after the call rejects exactly the inputs the checked kernel rejects, and the
  checked error bounds hold for every finite component.
- Which NaN a component holds when both operands are NaN is the target's IEEE choice; the VST
  models fix it to CompCert's `Float` operations.
- They have no Python binding, and the wrappers `diana_euler` and `diana_rk4` do not use them.
