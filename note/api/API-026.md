`diana.euler_step(y, f, h)`, `diana.rk4_stage(y, k, h, stage)` and
`diana.rk4_step(y, k1, k2, k3, k4, h)` return one C kernel call as a new `array.array("d")`;
`diana.euler(f, t0, y0, h, nstep)` and `diana.rk4(f, t0, y0, h, nstep)` loop over them in
Python, not through the C wrappers.

- The single-call functions read array arguments as in API-020, allocate the output
  themselves, and call the extension with it as `out`; the inputs are never modified. A length
  mismatch, then a non-finite component, raise `ValueError`.
- `euler` and `rk4` check, in order: `nstep` (`operator.index`, `TypeError`; negative
  `ValueError`), `t0` and `h` (`real`, `TypeError`), then copy `y0` element by element with
  `array("d", iter(y0))` (a `bytes` object becomes its integer values, not raw float64 data) and
  reject an empty one (`ValueError`). `nstep = 0` returns that copy.
- Times come from the step index: `euler` calls `f(t0 + k*h, y)`; `rk4` calls `f` at
  `t0 + n*h`, `t0 + (n + 0.5)*h` (twice) and `t0 + (n + 1)*h`, at the stage points
  `rk4_stage` builds.
- `euler` passes what `f` returns straight to `euler_step`: a buffer is read in place and must be
  a valid array argument (a NumPy `int64` array raises `TypeError`), any other iterable is
  copied. `rk4` copies every result of `f` element by element, so any iterable of numbers
  works and `f` may return the same buffer each time.
- `y` passed to `f` is the driver's current `array.array("d")`; `f` must not modify it, since
  the step reads it after `f` returns. Errors of the single-call functions propagate, and the
  partial trajectory is lost.
