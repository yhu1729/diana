title: Pipeline sources, six stages and the needs DAG

A pipeline exists only for a merge request, a push to the default branch, a tag matching
`^v\d+\.\d+\.\d+` or a schedule (`workflow: rules`); a push to any other branch without a merge
request runs no CI. Jobs belong to six stages, `style`, `build`, `test`, `report`, `verify`,
`release`, but start through `needs:` as soon as their dependencies finish:

- `build_{gcc,clang}_{debug,release}` need `style_c` (optional); each `test_<cc>_<config>` needs
  the build of the same name and runs on its `build/` artifact.
- `test_install` needs `build_gcc_release` but configures its own build directories.
- `coverage_c` waits for `test_gcc_debug`, `coverage_python` for `test_python`, `verify_frama_c`
  for `test_gcc_release`; all three needs are optional and fetch no artifacts.
- `test_python`, `verify_lean` and `verify_rocq` have `needs: []` and start at once; the four
  style jobs have no `needs:`, and only the builds wait for one of them (`style_c`).
- `release` needs the test and verify jobs (CI-014).

Defaults for every job: `interruptible: true`, so GitLab's auto-cancel of redundant pipelines can
stop a superseded pipeline's running jobs, and `retry: max: 1` only `when: runner_system_failure`
(a failing script is not retried). `GIT_DEPTH` is `1` except in `style_git` (CI-005). Timeouts:
`verify_lean` 2 h, `verify_rocq` 1 h, the rest the project default. The tag pattern has no end
anchor, so `v1.0.0-rc1` also starts a tag pipeline.
