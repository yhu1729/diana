title: style_git commit range from the GitLab variables
kind: fact
path:

---
`style_git` runs `script/check_commit.sh` with no argument (GIT-007) on `alpine:3.20` plus `git`,
in every pipeline: it has no `rules:`, because a commit needs checking whatever it touches, and
`GIT_DEPTH: "0"`, so every base commit is in the clone. It adds the checkout to git's
`safe.directory` first. The script takes its range from GitLab's predefined variables:

- head: `CI_MERGE_REQUEST_SOURCE_BRANCH_SHA` when set (a merged-results pipeline, whose own
  `CI_COMMIT_SHA` is the merge commit GitLab made), else `CI_COMMIT_SHA`;
- base: `CI_COMMIT_BEFORE_SHA` when it is not all zeros (a push to the default branch: the commits
  since that branch's previous pipeline), else `CI_MERGE_REQUEST_DIFF_BASE_SHA` (a merge-request
  pipeline: the merge request's commits);
- `base..head` when the base names a commit in the clone, else the whole history of head.

GitLab sets `CI_COMMIT_BEFORE_SHA` to zeros in merge-request, scheduled, manual and tag pipelines
and on a branch's first push. Tag and scheduled pipelines therefore check the whole history, as
does a force push whose previous head is no longer in the clone. The local fallback to
`@{upstream}` is skipped in CI, where `CI` is set. The GitHub `style_git` sets these variables from
its push event, the merge base with the default branch standing in for a merge request's base
(CI-019).
