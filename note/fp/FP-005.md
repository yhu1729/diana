The VST proofs are about CompCert's Clight semantics of the committed AST, so they carry to a
`ccomp`-compiled binary; the shipped library is compiled by gcc or clang. That the two compute
the same binary64 values is an argued and tested claim, not a theorem.

The argument: with the flags of FP-004 and `FLT_EVAL_METHOD == 0` (FP-003), a gcc or clang build
performs each source-level operation as one correctly rounded binary64 operation in source
order, which is the sequence the Clight AST and the Flocq model describe. This also needs the
runtime environment of API-001 (round-to-nearest-even, gradual underflow, traps disabled), which
no compiler flag establishes and Diana neither checks nor sets.

The evidence: `script/compare_compiler.sh` builds `src/*.c` with the corpus driver
`test/c/test_compiler.c` once with `ccomp` and with each available gcc and clang at `-O0`, `-O2`
and `-O3`, and fails unless every host build prints exactly the bytes of the `ccomp` build; the
driver prints statuses and doubles as bit patterns (COMPILER-001). It covers a finite corpus on
the machine it runs on, and runs only locally because CompCert is in no CI image.

What it does not cover: other targets than those compared, a compiler other than gcc or clang
(refused at configuration unless `DIANA_ALLOW_UNKNOWN_COMPILER` is ON, and then given none of
the strict flags, BUILD-013), and a caller that changes the floating-point environment.
