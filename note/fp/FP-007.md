---
id: FP-007
title: Configuration rejects fast-math and contraction flags
kind: rule
path:
  - CMakeLists.txt
  - test/c/test_configure.cmake
related: [FP-004, BUILD-013, TEST-043]
---
`CMakeLists.txt` stops configuration with a `FATAL_ERROR` naming the flag and the variable when
`CMAKE_C_FLAGS`, `CMAKE_C_FLAGS_DEBUG`, `_RELEASE`, `_RELWITHDEBINFO`, `_MINSIZEREL` or the one of
`CMAKE_BUILD_TYPE` contains a flag that permits anything but separately rounded binary64
operations in source order (an environment `CFLAGS` reaches it through `CMAKE_C_FLAGS`):

- fast-math and its parts: `-Ofast`, `-ffast-math`, `-funsafe-math-optimizations`,
  `-ffinite-math-only`, `-fno-honor-nans`, `-fno-honor-infinities`, `-fassociative-math`,
  `-freciprocal-math`, `-fno-signed-zeros`, `-fapprox-func`;
- contraction: `-ffp-contract=fast` (so also `fast-honor-pragmas`) and `-ffp-contract=on`;
- fast models: clang's `-ffp-model=fast` and `=aggressive`, Intel's `-fp-model=fast` and
  `-fp-model fast` (with any `=1` or `=2`).

It is a substring match, so `-fno-fast-math`, `-ffp-contract=off`, `-fno-associative-math`,
`-fsigned-zeros` and `-ffp-model=precise` pass; TEST-043 checks both sides. On gcc and clang the
strict options of FP-004 come after these variables on the command line, so the later
`-ffp-contract=off -fno-fast-math` is meant to win, but the guard does not rely on that order: it
makes the conflict an error. With `DIANA_ALLOW_UNKNOWN_COMPILER` (BUILD-013) it is the only check
left.

Not rejected: `-mfma`, and `-march=` values that imply FMA, which only make the instruction
available (AArch64 always has it) while `-ffp-contract=off` keeps it out of the arithmetic;
NVIDIA spellings such as `-Mfma` or `-fast`; options another project adds to the targets; and
the floating-point environment at run time (API-001).
