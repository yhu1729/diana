---
id: WP-002
title: No hexadecimal float literal in ACSL; write exact integer expressions
kind: rule
path:
  - src/bisection_mid.h
  - src/bisection_acsl.h
  - src/newton_acsl.h
related: [WP-001, WP-003]
---
No ACSL annotation uses a hexadecimal floating literal such as `0x1p970`: WP in Frama-C 32.1 (and
33.0) rejects one in a lemma and mistranslates one in a predicate. Write the value as an exact
integer expression instead.

`src/bisection_mid.h` defines the bisection bound `DBL_MAX/2 = (2^53 - 1) * 2^970` twice:

- `DIANA_BISECTION_MAX` is `(DBL_MAX / 2.0)`, for C code (`src/bisection_init.c` rejects larger
  endpoints with it); halving `DBL_MAX` is exact in binary64.
- `DIANA_BISECTION_MAX_ACSL` is `(((1 << 53) - 1) << 970)`, for ACSL, where integer arithmetic is
  unbounded, so the shift is exact. The contract of `diana_bisection_mid` and the uses of
  `bisection_bracket` in `src/bisection_init.c`, `src/bisection_step.c` and
  `src/bisection_result.c` take it.

The two macros must stay equal: the C guard establishes exactly the bound the ACSL predicate
states. Today no file under `src/` contains a `0x` literal.
