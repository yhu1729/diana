`script/verify_frama_c.sh` is the WP gate both locally (`script/dev.sh verify`) and in the CI job
`verify_frama_c`: for every row of `verification/frama-c/expectation.txt` it runs
`script/run_frama_c.sh` and then `script/check_frama_c.sh`, and it exits non-zero when any row
fails or the file has no row.

- `DIANA_JOB` rows run at a time, the value `script/job_count.sh` prints: `DIANA_JOB` itself (a
  positive integer, else an error), otherwise `nproc`, `sysctl -n hw.ncpu`,
  `getconf _NPROCESSORS_ONLN`, or 1. In CI, with the variable unset, that is the runner's CPU
  count. With more than one job, rows start in decreasing goal count (`sort -k2,2nr`) so the
  largest do not form the tail; with one job they run in file order.
- Each row gets `-wp-par ceil(4 / DIANA_JOB)`: 4 prover processes for a single row, 1 once four
  or more rows run at once, so about four Alt-Ergo processes are in flight overall. The 4 is the
  script's choice: `frama-c -wp-help` of WP 32.1 shows a default of 10 on the 10-core
  development Mac.
- `why3server` applies the 30 s timeout with `setrlimit`, a CPU-time limit. The recorded runs
  with ten rows at once prove every goal from an empty cache.
- Each row's output goes to a temporary file. After the last row, all outputs are written to
  `verification/frama-c/report.txt` (git-ignored; the CI artifact) under `==> <source> <==`
  headers in row order, then every row is checked even after an earlier failure: a failed WP run
  prints its last 20 lines, a passing one `<source>: [wp] Proved goals: P / T`.
